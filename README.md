# 低延迟撮合引擎（C++20）

[![CI](https://github.com/zdi28334-crypto/low-latency-matching-engine/actions/workflows/ci.yml/badge.svg)](https://github.com/zdi28334-crypto/low-latency-matching-engine/actions/workflows/ci.yml)

一个面向 A 股（上交所 / 深交所规则）的 C++20 低延迟撮合引擎，包含多线程分片撮合、集合竞价与连续竞价、多种市价单与自成交防范、Level-2 逐笔行情重建、WAL + 快照崩溃恢复、延迟观测与优化、基于 L2 逐笔数据的回测撮合模拟器（按真实队列位置成交，并用撮合引擎做真值验证）、Python→C++ 因子插件化、回放对比与股指期货基差监控。所有指标都由本仓库代码在本机实测得到，`scripts/run_all.sh` 一条命令即可全部复现。

```
./scripts/run_all.sh      # 编译 → 单测 → 基准 → L2 重建 → 回放对比 → 崩溃恢复 → 回测精度 → 因子校验 → 基差监控
./scripts/ci_check.sh     # CI 用的快速正确性检查（不跑基准）
```

依赖：g++ ≥ 11 / clang ≥ 14、CMake ≥ 3.16、Python 3 + numpy + pandas。无第三方 C++ 库。

## 2. 架构

```
                         ┌──────────── shard 0 (pinned CPU 1) ─────────────┐
 gateway ─ route(sym) ─► │ SPSC inbox ─► OrderBook[sym…] ─► EventBuffer    │──┐
 (stamp ingress TSC)     └─────────────────────────────────────────────────┘  │  LogRecord(40B)
          │              ┌──────────── shard 1 (pinned CPU 2) ─────────────┐  ├──► SPSC ring ─► logger thread ─► mmap 文件
          └────────────► │ SPSC inbox ─► OrderBook[sym…] ─► EventBuffer    │──┘   (格式化在热路径之外)
                         └─────────────────────────────────────────────────┘
   延迟打点:  ingress ──queue_wait──► dequeue ──match_core──► matched ──publish──► published
```

**为什么这样分片。** 同一证券的所有消息只进一个 shard 的单一 FIFO 队列，由单一线程处理。因此同一标的订单时序天然一致，不需要任何锁；不同证券在不同线程上并行撮合。一致性 Hash 的好处是扩缩容时只迁移约 1/N 的证券：单测里 4→5 个 shard 只有 21.6% 的证券换了归属，理想值是 20%。路由表在启动时预计算成数组，热路径上是 O(1) 查表。

### OrderBook 的低延迟设计（`include/me/order_book.h`）
- **数组档位**：A 股有涨跌停，所有可能价格事先已知。每一侧是一个按 `price - 跌停价` 下标的档位数组，查找档位 O(1)，没有红黑树的再平衡开销。
- **位图找最优价**：每侧维护一个“非空档位”位图。档位清空后，用 `clz/ctz` 几条指令就能找到下一个最优价，不用逐档扫描。
- **对象池 + 侵入式双向链表**：订单节点预分配，同价位按 FIFO 链接。撤单通过 `FlatMap<OrderId → 节点下标>` 定位，O(1) 完成。
- **FlatMap**：开放寻址加线性探测，删除用 backward-shift（不留墓碑），大量挂撤单之后探测链也不会变长。
- **热路径零分配、零 I/O**：撮合结果全部通过模板化的 Listener 回调传出，调用可以内联。

### 上交所集合竞价定价（`OrderBook::auction_price`）
按上交所交易规则依次判断：(1) 成交量最大；(2) 高于该价的买单、低于该价的卖单全部成交；(3) 该价位上买卖至少一方全部成交。仍有多个价格时取未成交量最小者，再并列则取中间价（这里实现为四舍五入到最小价位）。

单测 `call_auction_rules` 构造了一个反例：10.01 的成交量同样最大（1300），但违反条件 (2)，因为高于它的买单有 1500 股无法全部成交，所以最终定价 10.03。竞价阶段同一个函数还用于计算虚拟参考价。

### 主板价格笼子（`OrderBook::within_cage`，`CageConfig`）
连续竞价阶段的限价单要满足以下约束，否则拒单：
- 买入：申报价 ≤ max(买入基准价 × 102%，买入基准价 + 10 个最小价位)
- 卖出：申报价 ≥ min(卖出基准价 × 98%，卖出基准价 − 10 个最小价位)

买入基准价依次取卖一、买一、最近成交价、前收盘价；卖出基准价依次取买一、卖一、最近成交价、前收盘价。“10 个最小价位”这条兜底主要影响低价股：比如 2 元的股票，2% 只有 4 分钱，兜底放宽到 1 角。集合竞价阶段和市价单不受笼子约束。

比较全部用整数完成（`p*100 <= base*102`），避免浮点误差导致边界价被误判。参考实现 RefBook 故意改用浮点写法，与之独立对拍。另一种处理方式是把超出笼子的申报暂存、等笼子移动后再参与撮合，本项目未实现。上线前应以交易所最新发布的规则原文为准。

### 市价单类型（`OrdType`）
市价单只在连续竞价阶段接受，集合竞价阶段一律拒单。
| 类型 | 行为 |
|---|---|
| 最优五档即时成交剩余撤销 | 最多扫对手方 5 个价位，剩余部分撤销 |
| 最优五档即时成交剩余转限价 | 最多扫 5 个价位，剩余部分以最后一笔成交价转为限价单挂出；对手方为空时拒单 |
| 本方最优 | 以本方最优价作为限价挂出；本方为空时拒单 |
| 对手方最优 | 以对手方最优价作为限价，只吃这一个价位，剩余部分在该价挂出；对手方为空时拒单 |

### 自成交防范（`StpPolicy`）
同一账户（账户号非 0）的新订单在连续竞价中碰到自己的挂单时，按配置处理：
- `CancelNewest`：停止撮合，撤销新订单的剩余部分；
- `CancelOldest`：撤销那笔挂单，继续往后撮合；
- `CancelBoth`：两边都撤；
- `None`：允许自成交（默认）。

集合竞价阶段不做自成交检查。撤掉的挂单会通过 `on_cancel` 发出（行情里表现为撤单）。新订单被丢弃的剩余部分走单独的 `on_expire` 回调，并注明原因是 IOC 还是自成交。

### 上交所 / 深交所差异（`Venue`）
**集合竞价定价。** 两个交易所的前三条规则相同，"未成交量最小"之后仍然并列时，处理方式不同：
- 上交所：取剩余候选价的中间价；
- 深交所：开盘集合竞价取最接近前收盘价的价格，其他集合竞价取最接近最近成交价的价格（距离相同时取较低价，这一点为实现约定）。

单测 `szse_auction_closest_to_reference` 构造了同一组订单：上交所定价 10.01，深交所定价 9.97。

**逐笔行情口径**（`include/me/l2.h`）
| | 上交所 | 深交所 |
|---|---|---|
| 委托何时发布 | 挂上簿后才发布 A，数量是剩余量；到达即全部成交的主动单没有 A | 收到即发布 O，数量是原始量，先于它引起的成交 |
| 撤单 | 委托流里的 D | 成交流里的 C（对应 ExecType=4） |
| 市价单 | 不出现在委托流里 | 出现在委托流里，价格为 0 |
| 重建要点 | 成交里的主动方可能从未上簿，只扣减簿上真实存在的一方 | 收到即入簿，盘口会短暂交叉，直到随后的成交记录到达；剩余转限价的挂单价要从它最后一笔成交价推断 |

本次运行中，上交所口径有 815,162 笔成交的主动方从未上簿；深交所口径这个数是 0。两种口径重建出的盘口都与撮合引擎逐档一致，异常计数为 0。实现上做了一处简化：深交所的本方最优 / 对手方最优订单直接以转换后的价格发布。

### 崩溃恢复（`include/me/recovery.h`）
`DurableMatcher` 采用经典的 WAL + 快照方案：
1. 每条消息分配序号，**先写 WAL 再撮合**。WAL 写进 mmap 文件，进程崩溃后数据立即可见；要防断电，可以开启 `fsync`，在每次快照时 msync。
2. 每隔 N 条消息，把所有订单簿完整写入 `snapshot.tmp`（每笔挂单按 FIFO 顺序，加上交易阶段和最新价）。写完 fsync，再原子 rename 成 `snapshot.bin`，然后开新的 WAL 段 `wal-<seq>.log`，删掉旧段。
3. 恢复时先加载快照（序号 S），再从 S+1 开始重放 `wal-S.log`。每条 WAL 记录都带魔数和 CRC32，崩溃时写了一半的记录会因校验失败而被丢弃，重放到此为止。

撮合是确定性的，重放同样的消息必然得到同样的盘口。恢复完成后立刻做一次快照，上游网关从 `last_seq + 1` 开始重发。

| 崩溃时机 | 为什么安全 |
|---|---|
| 正在追加 WAL 记录 | 写了一半的记录 CRC 校验失败，被丢弃 |
| 正在写 snapshot.tmp | 旧的 snapshot.bin 和对应 WAL 段都还完整 |
| rename 之后、新 WAL 创建之前 | 快照已覆盖所有已接收的消息 |
| 旧 WAL 段删除之前 | 恢复只读和快照序号对应的那一段 |

`crash_test` 会 fork 子进程跑完整的订单流，在随机时刻 `kill -9`（不调析构、不刷缓冲），然后检查两件事：恢复出的盘口与"只处理前 last_seq 条消息"的参考结果完全一致，包括每笔挂单和 FIFO 顺序；续跑完剩余消息后，最终盘口与不中断跑完的结果一致。有几次恰好在写快照的过程中被杀，恢复程序正确地退回到上一份快照，并重放了完整的 WAL 段。

### 回测撮合模拟器（`include/me/backtest.h`）
**要解决的问题。** 回测时最难回答的是："我这笔挂单，在当时的市场里到底能不能成交、什么时候成交？"录制下来的行情里没有我们的订单，只能模拟。模拟得不准，回测结果就没有意义：挂单类策略最常见的失真，就是把成交率估高了。

**做法。** 用逐笔行情重建盘口，给策略的每笔挂单分配一个队列位置。沪深逐笔数据里每笔委托都有编号，所以队列可以**逐单精确跟踪**，不用靠估算：
- 订单到达时，排在同价位的订单都在我们前面。交易所委托编号随到达时间递增，所以只需记一个"截止编号"：当时该价位队列最后一笔的编号。
- 如果在我们价位上成交的那笔挂单编号大于截止编号，说明它比我们来得晚。现实中这笔成交应该先打到我们身上，所以我们成交。
- 如果成交价比我们的价格还差，说明主动单已经扫穿了我们的价位，我们成交。
- 如果有对手方订单最终挂在了穿过我们价格的位置上，说明它本该和我们成交，我们以自己的挂单价成交。
- 我们的订单到达时就能成交的，按价格优先、时间优先吃掉重建盘口里的可见挂单。吃掉的数量会记下来，同一份流动性不会被用两次。吃单途中碰到自己的反向挂单，按自成交防范撤掉。

作为对照，还实现了两种常见的简化模型：
- **touch**：价格一摸到就算全部成交；
- **through**：价格被穿过才算全部成交。

**怎么证明模拟得准。** 对同一段市场订单流跑两遍：
- **真值**：把策略订单真实插进撮合引擎，和原始订单流一起撮合。这是现实中会发生的结果。
- **模拟**：只用不含策略订单的录制行情来回测。

两边由同一个驱动和同一套策略代码运行。决策只在定时器上做（看到的是定时器时刻之前的全部事件），订单经过固定延迟到达，超过存活时间后撤单，决策只依赖市场状态而不依赖自己的成交。因此，只要两边看到的盘口相同，就会做出完全相同的决策，可以逐单比对成交量。

**A 股约束。**
- 订单只在连续竞价阶段提交，午休期间不决策；
- 进入收盘集合竞价前撤掉全部挂单；
- T+1：当天只能卖出底仓，当天买入的不能卖；
- 佣金双边收取，印花税只在卖出时收取，费率都可配置，示例参数仅作演示，以现行规定为准。

### Level-2 逐笔重建的验证
上交所口径下，到达即全部成交的主动单从来没有 A 记录，所以重建器处理成交时只扣减簿上真实存在的一方。最终用撮合引擎的真实盘口逐档对账。

### 延迟测量本身也要低开销（`include/me/latency.h`）
- **TSC 计时**：启动时检查 CPU 是否支持不变 TSC（`constant_tsc` + `nonstop_tsc`），支持则用 `rdtscp` 读时间戳计数器，并用 steady_clock 校准换算系数；不支持则自动退回 steady_clock。实测每次取时间 15 ns，steady_clock 为 21 ns。网关线程和 shard 线程在不同核上打点，跨核差值偶尔因微小偏差为负，这里统一截断为 0。
- **对数直方图**：思路同 HdrHistogram。低于 32 个 tick 的值精确计数，之上每个 2 的幂分成 16 个桶，相对误差不超过 6.25%。记录是 O(1)，内存固定约 1000 个计数器，多线程结果可以直接合并。原来的做法是每条消息往 vector 里写 4 个数，热路径上会有缓存污染和偶发的扩容。改用直方图后，异步日志模式的满负载吞吐从约 1.8–2.1 M msg/s 提升到约 2.4–2.8 M msg/s。

### 因子的 O(n) 滚动算法（`plugins/plugin_common.h`）
- 窗口和改为增量更新：加入新值、减去滑出窗口的旧值，复杂度从 O(n·w) 降到 O(n)。
- 反复加减会累积浮点误差，所以每 max(w, 16) 步做一次精确重算，摊销后每步仍是 O(1)。
- 方差不直接用 Σx² − (Σx)²/w，那样对价格序列会发生灾难性抵消。这里改为累计 (x − K) 的矩，锚点 K 在每次重算时设为窗口均值。
- 窗口很短（w ≤ 16）时直接计算：成本可以忽略，而且这种窗口的方差可能极小，累积误差在相对意义上会被放大。
- 结果：计算耗时 0.54 s → 0.055 s，约快 10 倍，与 Python 的最大相对误差仍为 8e-14。用 20 只 × 8000 根的长序列压测，最大误差为 2e-13。

## 3. 实测结果

测试环境：2 vCPU 云虚拟机，g++ 13，`-O2 -march=native`。合成订单流为 100 只证券、约 200 万条消息的完整交易日（开盘集合竞价 → 连续竞价 → 收盘集合竞价）。数值在不同次运行间有约 ±20% 的波动，表中给出的是多次运行的范围。

### 3.1 正确性（全部通过）

| 多线程分片引擎 vs 单线程 | 40 只证券的最终盘口逐档一致 |
| L2 重建盘口 vs 撮合引擎真实盘口 | 上交所口径 9,133 个价位、深交所口径 9,134 个价位全部一致；0 缺失 / 0 多余 / 0 数量不符 |
| 回测模拟 vs 真值（手工场景） | 排队位置、前方撤单、扫穿价位、挂单被反向单穿过、吃单与自成交防范、不重复吃同一份流动性，6 个场景在沪深两种行情口径下，队列模型的成交量和成交时间都与真值完全一致 |
| 崩溃恢复（随机时刻 `kill -9`） | 10/10 次恢复后盘口与参考结果完全一致，续跑后最终盘口也一致；WAL 尾部截断、中间位翻转、半写快照三种损坏场景单测通过 |
| C++ 因子 vs Python 参考 | 160/160 通过，最大相对误差 8.2e-14（容差 1e-9） |

模糊测试除了比对成交和盘口，还会检查一条不变量：连续竞价阶段买一价必须低于卖一价。这条可以证明集合竞价撮合结束后、以及各种市价单转限价之后，盘口都不会处于交叉状态。

### 3.2 撮合核心（单线程）
| 实现 | 吞吐 | 每条消息 |
|---|---|---|
| OrderBook（数组档位 + 位图 + FlatMap） | 9.4–13 M msg/s | 78–106 ns |
| RefBook（std::map + deque） | 2.3–3.0 M msg/s | 330–440 ns |
| 加速比 | **约 4×** | |

单条消息处理延迟：p50 约 180–200 ns，p99 约 0.63–0.74 µs。

### 3.3 非核心逻辑移出热路径（A/B 对比，1 shard，满负载）
| 日志方式 | 吞吐 | publish 阶段 mean / p99 |
|---|---|---|
| 同步：热路径 snprintf + fwrite + mutex | 1.04–1.12 M msg/s | 438–464 ns / 2.3–2.5 µs |
| 异步：40B 记录入 SPSC，mmap 落盘 | 2.4–2.8 M msg/s | 48 ns / 0.29 µs |

异步日志带来约 **2.3–2.5× 吞吐**，publish 阶段的 p99 降低约 **8×**，245 万条日志 0 丢失。（以上是改用 TSC 加直方图之后的数字；改造前用 vector 记录样本时，两者分别是 0.89–0.93 和 1.8–2.1 M msg/s。）

### 3.4 固定负载 100K msg/s 下的阶段延迟（1 shard，异步日志，绑核）
| 阶段 | p50 | p90 | p99 |
|---|---|---|---|
| queue_wait | 0.4–0.6 µs | 1.0–1.6 µs | 0.12–0.7 ms |
| match_core | 0.3 µs | 0.6–0.7 µs | 1.1–1.3 µs |
| publish | 0.1 µs | 0.2 µs | 0.5 µs |
| **e2e** | **≈1 µs** | **≈2 µs** | **0.12–0.7 ms** |

**e2e 尾延迟的来源。** 引擎自身（match_core + publish）的 p99 不到 2 µs，e2e 的 p99 几乎全部来自 queue_wait。`hiccup` 工具在一个空闲、绑核、只空转读时钟的线程上测了 5 秒，平台就出现了约 7,000 次 >10 µs、50–115 次 >100 µs、2–16 次 >1 ms 的停顿，最长 3–4 ms。这些是虚拟机调度和 steal time 造成的，任何程序在这台机器上都躲不开。在物理机上做 `isolcpus`、关中断亲和、关超线程后，尾延迟会显著下降，这是下一步该做的部署层优化。

### 3.5 回测成交模拟的精度（50 只证券、100 万条消息、只看挂单）
策略：每隔一段时间在每只证券的买一、卖一各挂一笔 100–300 股的单子，延迟 20 ms。"占比"指我们的挂单在盘口里的分量，由挂单间隔和存活时间决定。

| 我们的挂单占比 | 真值成交率 | queue 模型 | touch 模型 | through 模型 | queue 逐单完全一致 | through 逐单完全一致 | touch 逐单完全一致 |
|---|---|---|---|---|---|---|---|
| 轻（每 20 s 挂一次，存活 10 s） | 9.8% | 9.8% | 63.2% | 9.2% | **99.1%** | 98.1% | 46.0% |
| 中（每 5 s 挂一次，存活 30 s） | 21.7% | 21.4% | 84.1% | 19.1% | **93.4%** | 91.5% | 34.1% |
| 重（每 2 s 挂一次，存活 60 s） | 25.7% | 24.4% | 90.8% | 25.9% | **82.2%** | 79.4% | 29.7% |

（"逐单完全一致"只统计两边决策相同的订单。轻 / 中 / 重三档下，决策相同的比例分别为 98%、89%、65%。）

结论：
- **touch 模型严重高估成交**，挂单成交率被估成实际的 3.5–6.5 倍。用它回测挂单策略，结果会好得离谱。
- **queue 模型在占比小的时候几乎和真值一样**（99.1% 的订单成交量完全一致）。占比越大，偏差越大，这是录制行情回测的固有局限：录制的市场不会对我们的订单做出反应。我们在现实中成交时，会吃掉主动单的数量，让它扫得更浅；录制数据里，这笔量照样又被后面的挂单拿走了。所以策略在盘口中占比较大时，任何基于录制数据的回测都应该打折看待。
- through 模型的总成交率看起来也不差，但那是两种误差相互抵消的结果：它规则上偏保守（轻、中两档都低估了成交率），而在占比大时又因为同样没有市场冲击而多算。每一档的逐单一致率都低于 queue 模型。queue 模型的每条规则都对应真实的撮合机制。
- 沪深两种行情口径重建出的逐单状态完全一致，所以两种口径的回测结果也完全相同。这同时交叉验证了两条重建路径。
- 速度：queue 模型约 1–2.6 M 条逐笔记录/s（单线程）。为此做过一次优化：用"截止编号"代替每笔挂单维护一张"前方订单表"，速度提升约 3.4 倍。

### 3.6 其他
- 因子：160 个因子 × 45,000 行，C++ 0.055 s，比 Python（numpy 向量化）的 1.5–1.8 s 快约 30 倍，比优化前的 C++ 朴素实现快约 10 倍。
- L2 重建：222 万（上交所口径）/ 265 万（深交所口径）条逐笔记录，约 0.9 M 条/s，单线程且含 CSV 解析。
- 崩溃恢复：带 WAL 和每 10 万条一次快照的持久化撮合约 1.8–1.9 M msg/s；200 万条消息规模下，一次恢复（加载快照 + 重放最多 10 万条 WAL）耗时 50–160 ms。
- 基差监控：14,400 秒 × 2 个合约，两段注入的异常都被捕获，在正常区间内没有误报，异常结束后各发一条恢复消息。

## 4. 工程质量与 CI

每次 push 都会在 GitHub Actions 上运行 `.github/workflows/ci.yml`，包含：
- **build-test**：g++ 和 clang++ 各编译一遍，跑 `scripts/ci_check.sh`（单测、两种口径的 L2 重建对账、差分回放、golden 回归、`kill -9` 崩溃恢复、因子一致性、基差监控）。
- **sanitizers**：分别在 AddressSanitizer + UBSan 和 ThreadSanitizer 下跑全部单测。TSan 专门用来检查 SPSC 队列、异步日志这些无锁路径有没有数据竞争。
- **fuzz**：libFuzzer 跑 60 秒，对拍 OrderBook 和 RefBook，覆盖两个交易所、全部订单类型、自成交策略、逐笔行情重建和中途快照恢复。

cmake -S . -B build-tsan -DME_SANITIZE=thread  && cmake --build build-tsan --target unit_tests && ./build-tsan/unit_tests
cmake -S . -B build-asan -DME_SANITIZE=address && cmake --build build-asan --target unit_tests && ./build-asan/unit_tests
CXX=clang++ cmake -S . -B build-fuzz -DME_FUZZ=ON && cmake --build build-fuzz --target fuzz_book && ./build-fuzz/fuzz_book -max_total_time=60

## 6. 已知简化 / 可扩展方向
- 数据是合成的。真实上交所 L2 逐笔是付费数据，`l2_rebuild` 的输入是一个明确定义的 CSV 格式，接真实数据只需要写一个字段映射。
- 价格笼子只实现了“超出即拒单”，未实现“暂存后再撮合”的方式。
- 深交所模式只覆盖了集合竞价定价和逐笔口径两处差异；本方最优 / 对手方最优在深交所行情里简化为按转换后价格发布。
- 崩溃恢复目前接在单线程的 `DurableMatcher` 上。在多线程分片引擎里，网关可以充当定序器统一写 WAL，但各 shard 的一致性快照需要先让 shard 停顿（或按 shard 各自记录序号），这部分还没有实现。
- 回测模拟假设：委托编号随到达时间单调递增（沪深逐笔数据满足这一点）；不模拟我们的订单对市场的冲击（见 3.5）；策略订单只用限价单，不参与集合竞价；示例策略只用于验证模拟精度，不是盈利策略。
- 未实现：申报数量整手校验、自成交检查扩展到集合竞价、盘中证券迁移。
- L2 重建用的是 std::map 加 CSV 解析，约 0.9 M 条/s。改用数组档位和二进制格式可以明显提速。
- 基差监控的到期日按“合约月第三个周五”计算，未接节假日日历。
- 只有 2 vCPU，无法展示多 shard 的线性扩展；在更多核的机器上用 `--shards N --pin 1` 测试即可。
